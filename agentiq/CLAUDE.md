# CLAUDE.md — AI coding context for AgentIQ

This file orients any AI coding assistant (and any new human contributor)
working in this repository. Read this before writing code here. It
supplements — and must stay consistent with — [`../solution_plan.md`](../solution_plan.md).

## What this project is

AgentIQ is an AI-powered commercial intelligence platform for Urban Media,
a digital out-of-home (DOOH) advertising company. It turns a messy campaign
brief into a ranked, priced, optimised, and explained screen recommendation.
See [`../Hack Days 2026 Problem Statement.md`](<../Hack Days 2026 Problem Statement.md>)
for the full problem statement and [`../solution_plan.md`](../solution_plan.md)
for the phased build plan this codebase implements.

## The one rule that matters most: deterministic core, agentic edge

- Pricing math, relevance scoring math, reach/impressions math, and the
  optimizer are **pure, deterministic, unit-testable functions**. Given the
  same inputs they always produce the same outputs. No LLM call may sit
  inside these code paths.
- LLM agents are used **only** for: parsing unstructured briefs (Phase 4),
  semantic audience/environment labelling from a controlled vocabulary
  (Phase 3.3), bounded semantic re-ranking within a fixed band (Phase 5.3),
  orchestration/routing decisions (Phase 8), and narrative composition from
  already-computed numbers (Phase 8.4).
- **An LLM must never author a number that appears in a recommendation.**
  Narrative-composition output is validated against the structured payload
  before being returned; if a stated figure doesn't match, the response
  fails rather than showing an invented number.

## The `Explanation` contract (once Phase 2 lands)

Every public engine output that a user or judge might see carries an
`Explanation`: contributing signals with direction/weight, cited evidence
(table + row keys), a confidence level, and any fallbacks used. Do not add
a new scored/priced/ranked output type without also giving it an
`Explanation`. See `solution_plan.md` Step 2.2.

## Config over code

Never hardcode a city ID, zone name, POI type, price constant, or scoring
weight in engine code. These live in `config/*.yaml` and `config/cities/*.yaml`.
This is what lets a new city be onboarded with a data drop + a YAML file
and no code change (Step 10.2). If you find yourself writing
`if city_id == "LH":`, stop — that belongs in config.

## Repositories, not file paths

Engines depend on repository protocols (e.g. `ScreenRepository`,
`BookingRepository`) defined in `agentiq.data`, never on pandas frames or
CSV paths passed in directly. This keeps the hackathon in-memory/parquet
implementation swappable for a real database without touching engine code.

## Testing conventions

- Unit tests assert **numeric invariants** (e.g. `floor <= target <= cap`,
  concavity of the impressions curve, sub-additivity of reach) — never
  exact floating-point values pulled from a single run.
- LLM-produced output is checked for **schema validity and grounding**
  (every label comes from the controlled vocabulary, every claim cites
  real evidence IDs) — never for exact string equality.
- Acceptance tests are the six supplied campaign briefs (Step 2.5) run
  end-to-end. If a change breaks one of these without an explicit, reasoned
  plan update, treat it as a regression.

## Development sequencing: correctness before lint

When actively building or debugging engine logic, prioritize proving
functional correctness (tests passing against the real data, invariants
holding) over `ruff`/`mypy` cleanliness. It's fine to land a working engine
with outstanding lint findings (e.g. line-length) and note them in
`HANDOFF.md` as a follow-up — but always run `make lint`/`make typecheck`
and clear the backlog before Phase 10 packaging/submission. Don't let lint
churn interrupt the verify-the-logic-works loop while a feature is still
being built.

## Commands

```
make install     # create venv, install deps + package in editable mode
make data        # sanity-check raw CSVs are present
make profile     # regenerate docs/data_dictionary.md from data/raw
make build       # build precomputed artifacts into data/artifacts
make serve       # run the FastAPI app with reload
make test        # run pytest
make lint        # ruff check
make typecheck   # mypy
```

## Do-not list

- Do not have an LLM compute or adjust a price, score, or reach number directly.
- Do not hardcode any city-, zone-, or screen-specific logic in engine code.
- Do not let an engine read a CSV path or a pandas DataFrame passed ad hoc —
  go through a repository protocol.
- Do not hand-edit `docs/data_dictionary.md` — it is regenerated by `make profile`.
- Do not add a scored/priced/ranked output without an `Explanation`.
- Do not skip the Phase 1 data-discovery gate (`solution_plan.md` Step 1.9)
  before building on an assumed schema, distribution, or cardinality.
